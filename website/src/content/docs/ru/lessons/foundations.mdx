Тест пройден. Можно выпускать? Сначала выясним, что именно проверяли, чего ожидали и почему этому ожиданию можно доверять.

На нашем мероприятии десять мест. Небольшая функция решает, открыта ли запись. Два исходных теста проходят, но граничный дефект остаётся. Мы превратим это противоречие в полезный тест и сформулируем точный вывод об исправлении.

## Чему вы научитесь

После урока вы сможете:

- Получать ожидаемый результат из сформулированного требования.
- Выбирать значения перед границей, на ней и после неё.
- Писать воспроизводимый отчёт о дефекте и автоматический регрессионный тест.
- Объяснять, что подтверждает успешный тест функции и чего он не проверяет.
- Выбирать следующую проверку по риску, а не по количеству доступных инструментов.

Достаточно понимать функции, условия и логические значения. Если JavaScript незнаком, читайте `true` как «открыта», `false` как «закрыта», а `===` как строгое равенство. Первое упражнение можно выполнить в браузере без установки программ.

## Правило, которое можно проверить

Запись на мероприятие открыта, пока есть хотя бы одно свободное место. Для упражнения мы согласовали такое требование:

<div class="callout-rule"><p><strong>Запись открыта тогда и только тогда, когда число зарегистрированных меньше вместимости.</strong></p></div>

Функция получает два безопасных целых числа: `registered >= 0` и `capacity >= 1`. Она возвращает логическое значение. Некорректный ввод вызывает `TypeError`. При импорте данных число участников может оказаться выше вместимости; тогда функция должна вернуть `false`.

Эта функция только принимает решение. Она не добавляет участника, не резервирует место и ничего не сохраняет. Эту границу важно учитывать, когда мы объясняем результат теста.

Не заглядывая в код, предположите результат для 9, 10 и 11 зарегистрированных при вместимости 10. Объясните каждый ответ с помощью правила.

## Ожидаемый результат и наблюдение

**Ожидаемый результат** следует из требования. **Фактический результат** мы получаем при запуске реализации. Сравнение реализации с ней самой мало что даёт: нужно независимое основание ожидать конкретный ответ.

Источник ожидаемого поведения называют **тестовым оракулом**. Здесь это согласованное правило и простой подсчёт свободных мест. В других системах им может быть спецификация, независимый расчёт или мнение эксперта в предметной области. Оракул бывает неполным или ошибочным. Если правило допускает разные трактовки, уточните его, прежде чем объявлять поведение дефектом.

| Уже зарегистрировано | Свободных мест | Ожидаемое состояние записи |
| --- | --- | --- |
| 9 | 1 | Открыта (`true`) |
| 10 | 0 | Закрыта (`false`) |
| 11 | Вместимость уже превышена | Закрыта (`false`) |

Значения **9, 10, 11** находятся вокруг границы решения. Это небольшой пример анализа граничных значений. Здесь такой выбор полезнее множества произвольных чисел меньше десяти.

## Два зелёных теста могут пропустить дефект

В исходной реализации есть такая строка:

```js
return registered <= capacity;
```

При 9 участниках она возвращает `true`, при 11 возвращает `false`. Оба существующих теста проходят. Но при ровно 10 участниках оператор `<=` тоже даёт `true`. На равенстве реализация расходится с правилом.

Набор тестов представляет собой выбранные наблюдения. Зелёный результат не распространяется автоматически на случаи, которых в нём нет. «Два теста прошли» является точным фактом. «Запись работает правильно» уже гораздо более широкое утверждение.

Тестирование не ограничивается исполнением кода. Разбор правила, вопрос о листе ожидания, исследование интерфейса и поиск причины расхождения тоже относятся к тестированию. Автоматическое утверждение фиксирует одну воспроизводимую проверку внутри этого исследования.

## Превратим недостающий пример в тест

В небольшом тесте есть подготовка, действие и проверка. Мы используем встроенный раннер Node и строгие утверждения:

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { isRegistrationOpen } from './registration.mjs';

test('closes registration when the event is full', () => {
  // Given: ten people are registered for ten seats.
  const registered = 10;
  const capacity = 10;

  // When: we ask whether registration is open.
  const actual = isRegistrationOpen(registered, capacity);

  // Then: no seats remain, so registration must be closed.
  assert.equal(actual, false);
});
```

Код в обеих языковых версиях одинаков. `Given` задаёт исходные условия, `When` выполняет действие, `Then` проверяет результат. `assert.equal(actual, false)` завершится ошибкой, если функция вернёт `true`. Название теста описывает поведение, а не повторяет выражение из реализации.

Действуйте по порядку:

1. **Увидьте падение.** Добавьте тест равенства и запустите его на исходном коде. Убедитесь, что причина именно в неверном логическом результате, а не в сломанном импорте или команде.
2. **Исправьте реализацию.** Замените `<=` на `<`.
3. **Повторите проверки.** Новый тест и исходные примеры должны пройти. Проверьте другую вместимость, чтобы решение случайно не зависело от числа десять.
4. **Сохраните тест.** Он защищает от возвращения этого конкретного граничного дефекта. Это регрессионная проверка.

В упражнении мы добавляем тест к уже существующему ошибочному коду. Это не полная демонстрация разработки через тестирование (TDD); этот процесс разберём отдельно.

## Опишите дефект так, чтобы его воспроизвели

Полезный отчёт отделяет факты от возможных последствий:

> **Заголовок:** Заполненное мероприятие продолжает разрешать запись.<br />
> **Окружение:** Node.js 24; укажите ревизию репозитория или дату скачивания.<br />
> **Ввод:** `isRegistrationOpen(10, 10)`.<br />
> **Ожидается:** `false`, потому что число участников равно вместимости.<br />
> **Фактически:** `true`; приложите вывод падающего утверждения.<br />
> **Возможное влияние:** Вызывающий код может предложить запись, когда мест уже нет. Может ли полная система действительно продать лишнее место, зависит также от логики резервирования.

Фраза «запись сломана» заставляет читателя заново искать проблему. Минимальный ввод, наблюдаемый результат и явное правило помогают сразу перейти к следующему действию.

## Выбирайте следующую проверку по риску

Тест функции изолирует бизнес-правило. Он быстрый, а результат легко объяснить. Компонентный или интеграционный тест мог бы проверить сервис бронирования с настоящей базой. Сквозной тест (end-to-end) мог бы записать участника через браузер. Разные границы проверки отвечают на разные вопросы; больший охват системы сам по себе не делает тест лучше.

После исправления остаются важные вопросы:

- **Конкурентные запросы:** могут ли два клиента увидеть одно свободное место до того, как кто-то его зарезервирует?
- **Обратная связь в интерфейсе:** объясняет ли страница, что мест нет, в том числе пользователю клавиатуры или скринридера?
- **Актуальность данных:** использует ли решение свежий счётчик или устаревшее значение из кеша?

Учитывайте возможный ущерб, вероятность и стоимость получения полезных свидетельств. Для реальной продажи билетов проверка одновременного резервирования последнего места полезнее ещё двадцати успешных примеров этой чистой функции.

Тестирование начинается до реализации: уточняйте правило при планировании, проверяйте его при разработке, запускайте проверки в CI и наблюдайте за работой после выпуска. Наблюдения в продакшене дополняют управляемые тесты, но не заменяют их.
