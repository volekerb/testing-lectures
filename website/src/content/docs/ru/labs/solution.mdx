Сначала попробуйте выполнить [практику](../registration/). Полезное решение не сводится к изменению одного символа.

## Недостающий пример

Для `(9, 10)` ожидаем `true`, для `(10, 10)` и `(11, 10)` ожидаем `false`. Оракулом служит согласованное правило. В исходных тестах нет равенства.

Добавьте в `starter/registration.test.mjs`:

```js
test('closes registration when the event is full', () => {
  assert.equal(isRegistrationOpen(10, 10), false);
});
```

До исправления Node сообщает об ошибке утверждения: фактически `true`, ожидалось `false`. Это важное наблюдение: новый тест действительно обнаруживает данный дефект. Тест, который ни разу не падал, может вызывать не ту функцию или проверять несущественное значение.

## Минимальное исправление

Замените выражение возврата в `starter/registration.mjs`:

```diff
-return registered <= capacity;
+return registered < capacity;
```

Не меняйте проверку входных данных. Запустите свои тесты, затем `node check.mjs`. Ожидаемый результат: **6/6 checks passed**. Кроме 10, проверяются вместимости 1 и 20, поэтому константа вместо аргумента не решит задачу.

Эталонная реализация и тесты находятся также в `labs/registration/solution/` репозитория. Для сравнения запустите `npm run lab:solution` из корня репозитория. В скачиваемом задании этой папки специально нет.

## Вывод, который поддерживают наблюдения

> Теперь функция закрывает запись при равенстве числа участников и вместимости, сохраняя разрешение для проверенных примеров ниже границы. Новый регрессионный тест падает на исходной реализации и проходит после изменения сравнения. Мы проверили шесть примеров с допустимым вводом. Мы не установили, что приложение целиком предотвращает продажу лишнего места при конкурентных запросах. Следующим шагом я бы проверил атомарное резервирование последнего места: два клиента могут увидеть одно и то же свободное место.

Избегайте формулировок «все дефекты исправлены» или «протестировано на 100%». Практика не измеряет покрытие строк или ветвей. Даже полное покрытие кода не доказывало бы корректность всех требований и взаимодействий.

## Расширяйте набор осмысленно

Добавьте проверку, что некорректный ввод вызывает `TypeError`. Используйте другую вместимость, чтобы обнаружить случайную константу. Не добавляйте множество чисел только ради счётчика тестов: объясняйте, какую новую ошибку способен обнаружить каждый пример.

Для конкурентного резервирования пока опишите сценарий словами: остаётся одно место, одновременно поступают две попытки записи; ровно одна должна завершиться успешно, а итоговый сохранённый счётчик не должен превысить вместимость. Такой сценарий проверяет операцию резервирования и состояние, а не только логическую функцию.
