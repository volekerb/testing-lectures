How do we turn “build a great application” into a reasoned decision about its quality? This lecture follows a product from business need to operation. Testing belongs throughout that journey.

## Outcomes and route

## Start with a business need

The original story begins with “I want a great app” and develops into selling goods globally on mobile devices. That still leaves unanswered questions: which customers, which goods, which markets, what budget and deadline, and what outcome counts as success?

For our worked example, a small shop sells physical items. Clarify payment, inventory, delivery, cancellation, accessibility and failure behavior before selecting test tools. “Checkout works” is too vague to be an oracle.

**Example agreement, authored for this rebuild:** an order is confirmed only after payment is authorized and stock is reserved. A declined payment must not create a confirmed order. Retrying the same checkout request must not create a second order or charge. These are exercise assumptions, not universal rules for all shops.

**Discuss:** a payment times out, but the provider may have authorized it. What needs clarification before we can say what the customer should see?

## Roles are contributions, not job titles

An analyst clarifies the business need and acceptance examples. An architect chooses component boundaries and tradeoffs. UX work considers the whole journey, including errors and recovery. Developers implement and review changes. Testers investigate behavior and risk. Deployment, operation and support keep the service usable and feed observations back into development.

One person may perform several roles. Testing is not a final department that makes everybody else's work safe. Nor does shared ownership mean nobody owns a decision: name the people responsible for requirements, environments, release decisions and investigating failed checks.

## What testing includes

Testing evaluates work products and behavior to discover problems and provide information about quality. A finite set of checks cannot demonstrate the absence of every defect. Planning, analysis, design, preparation, execution and evaluation all contribute evidence.

A requirement review is **static testing**: we inspect without executing the product. Submitting a checkout request is **dynamic testing**. A written specification is valuable but may omit user needs such as keyboard access, understandable errors or acceptable response times. Make those expectations explicit with relevant people.

A **test oracle** is a source for deciding what should happen: an agreed rule, an independent calculation, a reliable reference or a domain expert. The expected result comes from that source; the actual result comes from observation. Copying the implementation into the expected result can repeat its mistake. An unclear oracle needs investigation before a confident defect claim.

## Testing throughout the lifecycle

| Work in progress | Useful testing question |
| --- | --- |
| Requirements | Are rules consistent, feasible and illustrated with examples? |
| Architecture and UX | What happens when a dependency fails or a person cannot use the default interaction? |
| Implementation | Do small rules and component interactions behave as intended? |
| Delivery | Does the build install, migrate data and work in its target configuration? |
| Operation | What are users experiencing, and can we detect and recover from failures? |

Sequential or waterfall models organize major stages in sequence. They can make late feedback costly; the diagram does not prohibit early reviews. The V-model connects development work products with corresponding test activities. It is a planning aid, not a rule to postpone test design.

**Iterative** work revisits and improves a solution; **incremental** work adds usable portions. A project can do both. A **spiral** model organizes cycles around risk analysis. **RAD** emphasizes rapid development and feedback, often through prototypes. These names describe different ideas, not interchangeable labels.

**Agile** emphasizes collaboration, frequent delivery and adaptation. Scrum is one framework and uses sprints; Agile does not require every team to use Scrum or a two-week cycle. Short iterations still need coherent test data, review and meaningful acceptance criteria. See the [Agile principles](https://agilemanifesto.org/principles.html).

## From a change to a release

A possible pipeline is:

1. Review the change and run static checks.
2. Run fast unit and component checks.
3. Exercise relevant API and integration behavior.
4. Deploy a known build to a test environment.
5. Combine targeted automation with exploratory, accessibility and other risk-based checks.
6. Review evidence and remaining risk; deploy with observation and recovery arrangements.

This is an example, not a universal stage order. Some checks run in parallel or on a schedule. Continuous integration keeps changes integrated and checked frequently. Continuous delivery keeps software releasable; continuous deployment automatically releases changes that satisfy the configured controls. A green pipeline reports the checks that ran, not all possible product qualities.

Staged rollouts and canaries can limit exposure and reveal production differences. Monitor meaningful outcomes and decide who can stop or roll back a release. Production testing requires an explicitly controlled scope and suitable data; prefer synthetic or minimized data for ordinary test environments. Observation after release complements earlier testing.

## Skills and responsibilities

The original lecture includes requirements, UX, UI, backend, databases, mobile and desktop behavior; environment configuration; automation; reports; and improvements to the testing process. These remain part of the course horizon.

Useful skills combine programming, test design, domain knowledge, debugging, data preparation, infrastructure literacy and communication. Choose an improvement because it produces useful evidence, not because its tool name is fashionable.

## Environments, data and isolation

Development, test and production environments serve different purposes. Teams may also need preview environments, staging or several parallel test environments. Record the build revision, configuration, dependency versions, feature flags, database schema and relevant test data. A name such as “staging” does not prove production equivalence.

**Example:** two parallel tests edit the same customer record. One expects the original address; the other changes it. The resulting failure may be an interference problem rather than a checkout defect. Give tests independent records or an explicit reset strategy, and clean up what they create. Fixed sleeps do not establish readiness.

Environment ownership is shared engineering work: agree who provisions, diagnoses and restores it. Infrastructure as code and repeatable setup can help. A local container does not automatically reproduce production scale, networking or configuration.

## Classify by independent questions

Avoid using one label to answer every question about a test.

| Axis | Examples |
| --- | --- |
| Scope | Unit, component, integration, system, acceptance |
| Quality concern | Functional behavior, performance, accessibility, security, reliability |
| Knowledge used | Black-box specification; white-box internal structure |
| Execution | Static review; dynamic execution; human investigation; automated check |
| Input or situation | Positive and negative cases |
| Purpose or timing | Smoke, confirmation, regression; alpha/beta feedback in a release context |

A negative case checks rejection or recovery. It **passes** when the system rejects invalid input correctly. Black-box does not mean manual, and white-box does not mean unit-only. Acceptance checks evaluate agreed needs; system checks address the behavior of the defined system. Local terminology may vary, so state boundaries and intent.

### Integration and end-to-end: the closing question

The recording ends with a question about integration versus end-to-end testing without a frontend. Consider `client → order API → payment adapter → database`.

A unit check might exercise a price calculation without external services. An integration check might use the real order repository and a real test database. A broader journey might create an order through the API, handle the payment callback and verify the stored result. It can be end-to-end for the **declared backend boundary** even without a browser.

If payment is simulated, say so: it does not establish compatibility with the live provider. A browser journey adds UI interactions but still may substitute external services. Describe the entry point, exit observation, real collaborators and test doubles. [Integration-test terminology varies](https://martinfowler.com/bliki/IntegrationTest.html); the evidence boundary is more useful than arguing over the name.

### Quality attributes need measurable questions

“Fast” is incomplete. For a performance exercise, agree on a workload, dataset, environment, duration, error limit and response-time target. For example, a proposed target of p95 below 800 ms at 50 requests/second needs stakeholder agreement; it is not a measured property of our shop. The 95th percentile is the value at or below which 95% of the observed response times fall.

Accessibility includes keyboard operation and understandable feedback; an automated scan alone is insufficient. Security needs threats, authorization boundaries and appropriate test scope. Use the [WCAG overview](https://www.w3.org/WAI/standards-guidelines/wcag/) and [OWASP testing guide](https://owasp.org/projects/web-security-testing-guide) as further references, not a promise that one lesson covers either discipline.

## Plan the investigation

A test plan answers what, why, how, who and when. Include scope and exclusions, risks, approach, data and environments, responsibilities, schedule, artifacts, entry/exit criteria, and conditions for stopping and resuming. The PDF's IEEE 829 example is a historical formal template. The goal here is a useful agreement, not copying a large document.

**Worked lean plan:** investigate checkout for one market and one currency on build X. Prioritize duplicate charges and lost orders above cosmetic spacing. Use rule checks, API/database integration and a small number of browser journeys. Exclude real-money transactions and other markets, recording those limits. Use isolated synthetic customers and the payment sandbox. The developer investigates service failures; QA coordinates scenarios; the product owner resolves acceptance questions and owns the release decision with the team.

Start when the build, environment and agreed rules are available. Stop if the payment sandbox or test data is unreliable; record blocked cases instead of marking them passed. Resume after recovery and a smoke check. A proposed exit condition is that critical agreed scenarios have usable evidence, severe unresolved defects are reviewed, and remaining risks are explicitly accepted. A deadline does not turn unknown behavior into a pass.

Risk combines the likelihood of an adverse outcome with its impact. Scores help discussion but do not create certainty. Revisit priorities when evidence changes.

## Design a test case

A case records an ID and purpose, requirement or oracle, preconditions, inputs, steps, expected results and cleanup/postconditions. Include enough detail for the intended reader to reproduce it.

**SHOP-03, declined payment:** given a synthetic customer, one available item and a sandbox payment method configured to decline, submit checkout once. Expect a clear decline response and no confirmed order. Inspect the agreed order state and stock behavior; whether stock is temporarily reserved must be specified. Remove the created test records. Do not infer “no charge” solely from the page text: choose an observation at the relevant boundary.

## Choose examples deliberately

### Equivalence partitioning

Suppose an item quantity accepts whole numbers from 1 through 5. Partition inputs into valid integers, integers below 1, integers above 5, and invalid types or formats. Representative values might be 3, 0, 6 and `"abc"`. Type coercion and fractional inputs need an explicit contract. Members of a partition are treated as similar for this purpose; that is a test-design assumption, not proof that every member behaves identically.

### Boundary-value analysis

For that quantity rule, useful values include 0, 1, 2 and 4, 5, 6. Boundaries supplement partitions. The supporting registration lab isolates one boundary: registration is open exactly when `registered < capacity`.

Both arguments are safe integers; `registered >= 0`, `capacity >= 1`. Invalid inputs throw `TypeError`; an already-over-capacity count returns `false`. The function makes a decision; it does not reserve or persist a seat. Predict 9, 10 and 11 for capacity 10 before checking:

### Cause and effect: a decision table

For the exercise rule “confirm only if payment is authorized AND stock is reserved”, enumerate the combinations:

| Authorized | Reserved | Confirm order? |
| --- | --- | --- |
| No | No | No |
| No | Yes | No |
| Yes | No | No |
| Yes | Yes | Yes |

The table makes missing outcomes visible. Compensation, timeouts and retries require further rules; a Boolean table does not model the full asynchronous workflow.

### Pairwise, exhaustive and experience-based selection

Three browser engines × two locales × two payment methods produces 12 combinations. Exhaustive execution covers all 12 combinations of **those selected factors**, not every possible application state. Six carefully chosen rows can cover every pair of factor values: Chromium/EN/card, Chromium/RU/wallet, Firefox/EN/wallet, Firefox/RU/card, WebKit/EN/card, WebKit/RU/wallet. Three-way interactions may still be missed. Constraints can change which rows are valid.

Error guessing uses experience, such as checking duplicate submissions after a timeout. Exploratory testing combines learning, design and execution with a purpose: “For 15 minutes, investigate recovery after a checkout timeout; record actions, observations, questions and risks.” It is not random clicking. Preserve evidence so someone can continue the investigation.

## Cases, checklists and suites

A detailed case helps with reproducibility, handover or a subtle setup. A checklist is appropriate when a knowledgeable tester can supply the detail: empty cart, decline, retry, keyboard path, error recovery. An exploratory charter states the mission and timebox. Choose the artifact to suit the task.

Group checks by purpose and cost. A smoke suite asks whether critical behavior is usable enough to continue. Regression checks look for unintended changes. Performance suites need their own workload and measurements. Tagging by component, risk, environment and runtime helps select work without losing traceability.

For a large suite, investigate flaky results: uncontrolled state, timing, shared data, unstable dependencies or genuine intermittent defects. Reruns can aid diagnosis but do not erase the first failure. If a check is quarantined, record its owner, reason, risk and a deadline for repair. Parallel execution needs isolation, not just more machines.

## Describe the defect so someone can reproduce it

A defect report needs a short specific title, environment and revision, preconditions, steps or minimal input, expected and actual results, evidence and impact. Distinguish an observed failure from a suspected cause.

**Example:** “Full event reports registration open.” On the recorded Node version and source revision, call `isRegistrationOpen(10, 10)`. Expected `false` from the capacity rule; actual `true`. Attach the assertion output. A caller could offer an unavailable seat; an actual production oversell has not been demonstrated.

**Severity** describes impact; **priority** describes when to address the issue in context. A serious defect in a disabled feature and a prominent typo before a campaign may have different scheduling considerations. Do not equate priority with an intrinsic property of the code.

A typical workflow is report → triage → fix → confirmation → closure or reopening. Names vary by team. Confirmation checks the specific fix; regression checks other behavior that the change may affect.

## Make the missing evidence executable

This optional worked test prepares you for the supporting lab. The starter passes checks at 9 and 11, but uses `<=` and mishandles equality. Add:

```js
test('closes registration when the event is full', () => {
  const actual = isRegistrationOpen(10, 10);
  assert.equal(actual, false);
});
```

The starter already imports `test` from `node:test`, `assert` from `node:assert/strict`, and the function. First observe the expected `false` versus actual `true` assertion failure. Then change `<=` to `<`, rerun all checks and retain the new test. An import error is not the intended failure. See the [lab instructions](../../labs/registration/) for commands and the ten-point rubric.

A passing function test does not show that two concurrent requests cannot reserve the same last seat. That needs a test of the state-changing operation and its persistence boundary.

## Report evidence and remaining risk

Reports support decisions for different readers. An engineer needs reproduction details and logs; a release owner needs coverage of important risks, unresolved defects and constraints. Include build, environment, time, scope and definitions of statuses.

**Illustrative report, not a real course run:** of 20 planned cases, 14 passed, 2 failed, 3 were blocked by the payment sandbox and 1 was not run. That is 14/16 among executed cases and 14/20 of all planned cases. Neither percentage tells us whether the most important risks are covered. Name the failures, blockers and next action; do not count blocked work as a pass. Mark stale results and explain how flaky attempts are counted.

A consistently passing test can be valuable protection. Review assertions, risk relevance, redundancy, runtime and diagnostic usefulness before removing it. Deliberately introducing a representative fault, or mutation testing where appropriate, can reveal weak assertions. Counting tests or celebrating a high pass rate is not a substitute for judgment.

## Tools and practical challenges

Choose a tool for a job: issues for defect tracking, a case repository for traceability, reports for evidence, diagrams or prototypes for shared understanding, data generators for repeatable inputs, browser tools for UI investigation, and load tools for performance. The archive shows products available then; those screenshots are not a current purchasing recommendation.

Browser engines and devices differ. [Playwright supports Chromium, Firefox and WebKit](https://playwright.dev/docs/browsers), but those engines do not cover every physical device or assistive technology. Prioritize a platform matrix using actual user and product needs.

Production-like datasets need meaningful shape and relationships, not copied personal information. Resilience investigations can include a controlled dependency failure in an authorized test environment, with an expected recovery behavior, observation and stop condition. This introduces the recording's fault-injection discussion; it is not a request to disrupt a public service.

## Homework: 20 cases for one application

The original PDF asks for 20 cases for a website. Preserve that assignment: choose an application you own, a local demo, or a site where the proposed non-disruptive testing is permitted. Designing cases does not require executing unsafe actions on a third-party service.

Submit:

1. A short product goal, declared boundary and assumptions; a lean test plan with three prioritized risks.
2. **20 distinct cases** using the case structure above. Include positive and negative scenarios, boundaries, at least one interaction and one quality attribute. Do not inflate the count with identical cases using arbitrary values.
3. A map from cases to requirements/risks and the techniques used; explain one deliberate exclusion.
4. Execute a safe smoke subset where feasible and report actual outcomes. If you only designed cases, label them **not run**. Report a reproducible defect only if observed; otherwise record an open question or risk.
5. A brief release recommendation with limitations and the next most useful investigation.

Assessment: scope and oracle clarity (2), meaningful case selection (3), reproducible case detail (2), honest evidence/reporting (2), and justified priorities (1). Total 10. The separate [registration lab](../../labs/registration/) has its own rubric and does not replace these 20 cases.
